## 2026-10-06 10:37:38 —— 新增同步故障注入回归测试（P0-1 / P2-4）

`SyncEngineTests` 新增 5 个用例（复用 `FakeStorageBackend` 的 `GetFault`/`PutFault` 故障注入），总计 153 → 158 通过：

- `PartialDownloadFail_FailedRemoteIdIsNotUploaded`：远端较新但 GET 失败的 id 被隔离，本地上传为 0，云端新内容原样保留，本地旧版本留待下轮重新裁决（P0-1 主场景）。
- `PartialDownloadFail_OtherLocalNotesStillUpload`：隔离只针对失败 id，其余差量照常上传、健康对象照常下行。
- `UnreadableRemoteObject_IsNotOverwrittenByLocalUpload`：坏 JSON（skippedInvalid 分支）同样隔离，零 PUT（P0-1 的确定性场景）。
- `PartialUploadFail_ReportsFailedIdsAndKeepsSuccess`：单条 PUT 503 不终止整轮，成功数与失败 id 如实进摘要（P2-4）。
- `AllUploadsFail_RoundFails`：全部上传失败仍判整轮失败（认证/配额边界）。

边界说明：远端只有一个对象且其 GET 失败时，「部分失败」与「全部失败」不可区分，仍命中既有的「全部下载失败即中止」闸（`AllDownloadsFail_RoundFails` 已覆盖），故两个部分失败用例均额外放置健康远端对象构造真正的部分失败场景。数据安全上两种处理等价——中止时不发生任何上传，隔离时失败 id 不参与对账。

## 2026-10-06 10:24:40 —— 第二批修复（P0-1 云端覆盖 + P2-4 上传部分失败 + P1-4 导入守卫）

- **P0-1 部分远端读取失败被误判为「远端不存在」导致云端被静默覆盖（本轮唯一 P0）**：`SyncEngine` 下载阶段新增 `incompleteIds` 隔离集合——网络失败、对象为空/超限、JSON 解析失败、解密失败的对象 id 一律记入（id 优先取 DTO，其次从协议 key 解析）；全量对账循环对这些 id **跳过裁决（不上传也不下载）**，从语义上区分「确认不存在」与「读取失败」，并在摘要 `SyncRoundSummary.IncompleteCount` 留痕。`SyncProtocol.TryGetNoteId` 复用现有解析。云端新数据不再可能被本地旧版本覆盖。
- **P2-4 上传单条失败即终止整轮、已成功成果全部丢失**：上传循环改为逐条 try/catch，累计成功数与失败 id（摘要新增 `UploadFailedIds`）；仅当**全部**上传失败才抛异常。`SyncHost` 对部分失败记入 `LastError` 供设置页展示；主列表「立即同步」提示条区分「全部成功」与「上传失败 N 条（下轮自动重试）」。下行已应用时 UI 刷新不再被上传异常吞掉。
- **P1-4 JSON 导入「先读后写」无守卫**：`NoteRepository.SaveBatchAsync` 的 Upsert 增加 `WHERE excluded.UpdatedAt > Notes.UpdatedAt` 条件守卫（已确认该方法全项目仅导入一个调用方），在事务内杜绝旧备份覆盖防抖窗口内的用户编辑；Service 层的快速裁决保留。

以上改动经 `dotnet build`（0 警告 0 错误）与 `dotnet test`（153 通过/0 失败）验证。
