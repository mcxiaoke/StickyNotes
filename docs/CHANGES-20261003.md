## 2026-10-03 21:35 (GMT+8) — 修复：托盘菜单致任务栏「展开图标」被白框圈住（我引入的回归）

> 用户报告：点托盘右键菜单里的菜单项（如「设置中心」）后，任务栏通知区域的
> 「显示隐藏的图标」按钮被白框圈住并获得焦点，同时弹出该按钮的提示文字。

### 根因（两个叠加因素）
1. **`NIM_SETFOCUS` 误用**（我在上一轮"顺带"加的）：实测该调用会把**整个任务栏**
   （`Shell_TrayWnd`）变成前台窗口（验证方式：菜单关闭后读取 `GetForegroundWindow()`，
   结果由 `Chrome_WidgetWin_1` 变为 `Shell_TrayWnd`）。Windows 随之给通知区域中
   获得焦点的图标绘制焦点框并弹出提示。该 API 的设计用途是"键盘触发菜单后按 ESC 取消"
   时归还焦点，不适合每次菜单关闭都调用。
2. **误删 `WM_CANCELMODE`**：上一轮为排除嫌疑我删掉了项目原有的 `WM_CANCELMODE`，
   而它是告知 Shell「菜单模式已结束」的必要信号。缺失后 Shell 会认为菜单仍处于激活态，
   转而去接管通知区域焦点 —— 与因素 1 叠加，形成该现象。

### 修复
- **移除 `NIM_SETFOCUS`**（不再向通知区域索取焦点）。
- **恢复 `WM_CANCELMODE`** 并**补 `WM_NULL`**：前者复位图标状态并告知菜单模式结束，
  后者是经典托盘菜单收尾（把前台身份干净交还给系统）。
- `NativeMethods` 新增 `WM_NULL` 常量。
- 托盘右键菜单弹出时增加一条 Info 日志，便于后续真机排查。
- 新增回归用例 `F_P1_8_TrayIcon_DoesNotStealFocusFromShell`：**源码扫描**锁定两条约束 ——
  有效代码中不得出现 `NIM_SETFOCUS`，且**必须**保留 `WM_CANCELMODE` 与 `WM_NULL`
  （扫描时剔除注释，避免说明性文字误判）。

> 用户报告并附截图：托盘右键菜单出现在屏幕右下角，远离托盘图标。

### 根因
上一轮修复托盘事件解码时，我顺手把菜单定位从 `Placement=MousePoint` 改成了
`Placement=AbsolutePoint` + 消息 wParam 中的锚点坐标，理由是"用真实点击点更可靠"——**这个改动是错的**：

- v4 下 `wParam` 携带的是 **物理像素**坐标（`GET_X/Y_LPARAM`）；
- WPF 的 `ContextMenu.HorizontalOffset/VerticalOffset` 单位是 **DIP**。

在 150% 缩放（本机 DPI 144）下，把物理值当 DIP 用会放大约 1.5 倍：
若点击点靠近屏幕右侧，换算后坐标直接越界，WPF 将菜单**钳到屏幕右下角**。

### 修复
改回 `Placement = MousePoint`：该模式下 WPF 自己在**屏幕 DIP 空间**内部定位，天然正确。
并补注释写明「禁止用 AbsolutePoint + 物理像素锚点」，避免以后又被"更精确"的直觉带回去。

### 缺陷 1（致命）：托盘事件码取错位段 → 左右键、双击全部失效
`TrayIconService.HwndHook` 原写 `int eventId = lParam.ToInt32();` 再与 `WM_LBUTTONUP` 等比较。

但同一批次新加的 `NIM_SETVERSION(NOTIFYICON_VERSION_4)` **改变了 Shell 的投递编码**：
v4 下 `LOWORD(lParam)` 才是通知事件（`NIN_SELECT` / `WM_CONTEXTMENU` …），`HIWORD(lParam)` 是图标 ID。
因此 lParam 实际形如 `0x03E9_0400`，既不等于 `0x0202` 也不等于 `0x0400`/`0x007B` —— **所有分支全部落空**，
托盘图标在但完全无响应。

来源依据：Microsoft Learn《NOTIFYICONDATA 结构》uCallbackMessage 一节与《Shell_NotifyIconW》Remarks
（v4 差异：左键/键盘激活发 `NIN_SELECT`/`NIN_KEYSELECT`，右键与键盘菜单键都发 `WM_CONTEXTMENU`，
旧版才发 `WM_RBUTTONDOWN/UP`）。

**修复**：新增纯函数 `NativeMethods.ClassifyTrayEvent(lParam)`，按 `LOWORD` 解析并返回
`OpenList` / `ShowContextMenu` / `None`；兼容旧版鼠标消息。同时新增 `LowWord` / `HighWord` 助手，
菜单锚点改用 wParam 中的真实点击坐标（`GET_X/Y_LPARAM`）而非 `Placement=MousePoint`。

### 缺陷 2（致命）：唤醒消息按"本进程"筛选 → 第二实例命中零个窗口
`NotifyExistingInstance` 改为 `EnumWindows` + `GetWindowThreadProcessId` 后，
用 `Environment.ProcessId` 筛选"本进程"窗口。但**本方法的调用方正是第二实例**，
第二实例自身没有任何窗口 → 匹配到 0 个窗口 → 唤醒静默失效。

**修复**：改为按**应用标识**（同可执行文件名）匹配，新增可测的
`NativeMethods.IsSameApplicationWindow(hwnd, currentProcessName)` 与纯函数 `IsSameProcessName`；
仍保留"不得使用 HWND_BROADCAST"的约束（UIPI 下会静默失败）。

### 缺陷 3：唤醒消息只挂在主列表窗口 → 后台启动时无人处理
`WM_ACTIVATE_INSTANCE` 原本只在 `NotesListWindow.WndProc` 处理。但在 `--minimized` / `--autostart`
路径下 `App.OnStartup` **不会调用 `mainWindow.Show()`**，因此主列表窗口没有 HWND，

> 用户报告：空白便签归档后，归档窗口的「清空归档」按钮是灰色的（无法点击）。

### 根因
`ArchivedNotesWindow.xaml:77` 的按钮绑定 `IsEnabled="{Binding CanClearArchived}"`，而
`CanClearArchived => ArchivedNotes.Count > 0` 是**从集合内容派生的计算属性**，其变更通知
仅由 `[NotifyPropertyChangedFor(nameof(CanClearArchived))]` 挂在 `ArchivedNotes` 这个
**属性 setter** 上生成。

但 `ArchivedNotesViewModel` 所有增删都是对**同一个集合实例**做原地 `Clear/Add/Remove`
（集合属性本身从未被重新赋值），因此该自动通知**永远不会触发**。实际发出的三个通知是
方法体内手写的 `FilteredNotes` / `ArchivedCount` / `HasNoNotes` —— **恰好漏掉了
`CanClearArchived`**。

后果：按钮停留在窗口首次绑定时的取值。首次打开归档窗口时 `ArchivedNotes` 为空，
`CanClearArchived` = `false` → 按钮**永久保持灰色**，即使归档列表随后被填充。
（与便签是否空白无关，任何归档便签都会复现；空白便签只是用户最先注意到该按钮的场景。）

### 修复
- `ArchivedNotesViewModel` 新增私有方法 `NotifyDerivedCollectionsChanged()`，一次性发出四个派生属性
  （`FilteredNotes` / `ArchivedCount` / `HasNoNotes` / `CanClearArchived`）的变更通知。
- 四处原地修改集合的路径全部改走该方法：`LoadArchivedNotesAsync`、`RestoreNoteAsync`、
  `HardDeleteNoteAsync`、`ClearAllArchivedAsync` —— 同时消除原先三行通知的重复粘贴。
- 在 `CanClearArchived` 上补 XML 注释，写明「由集合内容派生、必须显式通知」这一约束，
  防止后续再次漏发。
- `ArchivedNotesWindow.xaml` 给按钮加 `x:Name="ClearAllButton"`，使该缺陷可被 UI 级用例锁定。

### 验证（先复现后修复）
新增 2 个用例，**修复前均失败、修复后均通过**：
1. `ArchivedNotes_CanClearArchived_NotifiesWhenListLoads`：断言 `LoadArchivedNotesAsync` 后
   必须发出 `CanClearArchived` 的 `PropertyChanged`，且空内容便签也能进入归档列表。

## 2026-10-03 12:04 — 新增 PIN 锁定（防偷窥轻量保护）与列表闲时自动收起

### PIN 锁定

- 设置窗口新增「隐私保护」分组：启用/修改/清除 PIN，修改与清除均需先验证当前 PIN，防止他人绕过设置关锁。
- PIN 规则：4~20 位、内容不限，普通 PasswordBox 输入、Enter 确认；定位为防偷窥轻量保护，不做应用内找回（遮罩上有指引：退出应用后手动删除 settings.json 中 PinEnabled/PinSalt/PinHash 三个字段即可重置）。
- PIN 不存明文：PBKDF2-SHA256（2 万次迭代）+ 16 字节随机盐后写入 settings.json，验证采用恒定时间比较。
- 锁定呈现为窗口内不透明遮罩（新控件 PinLockOverlay，复用于列表与归档窗口），不引入独立解锁窗口与全局解锁状态；错误时抖动 + 红字提示。
- 锁定规则：列表窗口每次从不可见变为可见（应用启动、托盘/热键唤醒）都重新上锁；窗口保持打开期间不重复打扰。桌面贴纸不上锁。
- 归档窗口打开时：若主列表处于解锁可见状态则直接放行（视为刚验证过身份），否则同样上锁，避免绕过列表直取归档内容。

### 闲时自动收起

- 列表窗口（及归档窗口）持续不在前台达到设定分钟数后自动关闭/收起到托盘，下次打开需重新输 PIN（若已启用）。
- 设置项默认 10 分钟，可选 不启用/1/5/10/30 分钟；实现为 Deactivated/Activated + DispatcherTimer，不追踪键鼠输入。
